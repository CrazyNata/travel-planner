# Рефакторинг Android-приложения (mobile/)

## Context

Нативное Android-приложение в `mobile/` (Kotlin + Jetpack Compose, один модуль `:app`)
за 2.5 недели разработки выродилось в один файл на 18 тысяч строк. Рефакторинг нужен
не ради красоты — монолит уже приводил к потере всего приложения.

**Почему сейчас:**

- `mobile/app/src/main/java/com/odyssey/travelplanner/ui/OdysseyApp.kt` — **18 135 строк**,
  79% всей кодовой базы (весь Kotlin — 23 584 строки в 26 файлах). Внутри 281 top-level
  декларация, 162 composable и **ноль классов/объектов** — плоский суп из функций.
- Файл растёт линейно и не замедляется: 4 009 строк (1 авг) → 8 996 (5 авг) →
  13 752 (14 авг) → 18 135 (18 авг), это ~830 строк в день.
- **128 коммитов трогают этот один файл** — он стал единственной точкой изменений,
  любые две задачи конфликтуют между собой.
- Инцидент, ради которого всё затевается: коммит `f28be2b` должен был внести 409 строк,
  а фактически **удалил 12 934** — почти всё приложение. Дифф такого размера невозможно
  отревьюить, поэтому пропажу заметили только через три коммита, и `7251129` вернул
  12 648 строк обратно.

**Цель:** разнести монолит по фичам и завести слои — state-holder'ы (ViewModel), доменные
модели с типами вместо строковых литералов, явная навигация, единый слой ошибок и внедрение
зависимостей. Визуально и по поведению приложение остаётся прежним.

**Область работ:** только `mobile/`. Веб-приложение в `src/` не трогаем.

## Решения заказчика

| Вопрос | Решение |
| --- | --- |
| Глубина | Распил **+ нормальная архитектура** (ViewModel, доменные модели, навигация, слой ошибок) |
| Способ выкатки | **Одним большим заходом** |
| Тестовая страховка | **Не вкладываемся**, проверка ручная по экранам |
| Локализация | **Полный переезд**, включая доменные константы |
| Найденные баги | **Чиним в этом же заходе** |

Риск «один заход без тестов» принят осознанно. Компенсация, не требующая написания тестов, —
механическая инвентаризация деклараций до и после (см. «Проверка»): она ловит ровно ту
ошибку, что уже случилась в `f28be2b`.

### Важное уточнение по доменным константам

Русские строки в этом коде — не только UI. Это одновременно формат хранения и управляющий
словарь: `status == "бронь"`, `category = "Еда и рестораны"`, и главное —
**проверка прав `overview.currentUserRole == "Владелец"`** (`OdysseyApp.kt:5800`).

Проверено: тот же Supabase-payload читает веб-приложение `src/App.tsx` (само по себе монолит
на 10 445 строк), и там те же литералы — `Владелец` ×4, `бронь` ×17, `хочу` ×15.

Поэтому «полный переезд» выполняется так: **enum'ы вводятся во всём Kotlin-коде, а русские
строки остаются ровно в одном месте — кодеке на границе сериализации.** Формат хранения
в БД не меняется. Это даёт типобезопасность (никаких сравнений ролей по строке) и при этом
не ломает веб и существующие поездки. Менять сам формат хранения означало бы синхронную
правку веба плюс миграцию данных — веб из области работ исключён, а `AGENTS.md:10` прямо
запрещает трогать данные существующих поездок.

Каждый экран сам себе state-holder. Рекордсмены: `RestaurantsContent` — 31 переменная

## Слой данных: что нашли

**DI отсутствует полностью** — ни Hilt, ни Koin, ни ручного контейнера, ни класса
`Application`. Корень графа — глобальный `object SupabaseProvider`
(`data/SupabaseClient.kt:55`).

`interface TripRepository` (`data/TripRepository.kt:304`, 54 метода) **существует, но ни разу
не используется как тип** — везде названы конкретные классы. Шов для подмены формально
есть, фактически непригоден.

**Мёртвые кэши как следствие отсутствия DI.** `photoCache` в `SightCatalogRepository:168`
и `RestaurantCatalogRepository:173` живут на экземпляре, а экземпляры создаются заново на
каждый вызов → кэш всегда пустой. `CityCatalogRepository` держит распакованный TSV (~19 МБ
одной строкой) в `lazy`-поле, и при двух живых экземплярах строка существует дважды.

**Ошибки — четыре несовместимых канала** и ни одного типа-обёртки: `require`/`check`
с русскими пользовательскими строками (~30 мест), `error("Путешествие не найдено")`
(~20 мест), единственный типизированный `AuthSessionRequiredException` (проверяется ровно
в одном месте UI, `:4402`) и молчаливое проглатывание через `runCatching{}.getOrNull()`.
В data-слое 59 `runCatching`, в UI — 98, и `CancellationException` в них теряется.

**Дублирование в data-слое:** преамбула вызова Edge Function повторена **6 раз**;
`placesLanguageCode()` скопирован дословно **3 раза**; литерал бакета `"trip-photos"` —
**18 раз**, хотя константа `TRIP_PHOTO_BUCKET` уже есть в `TripPhotoStorage.kt:15`;
локальные `fun text(key)` переопределены **9 раз** внутри `TripRepository.kt`.

**Самые тяжёлые функции:** `loadTripOverview:477` — 246 строк и минимум 4 обязанности;
`updateTripDetails:1123` — 102 строки с полной регенерацией массива дней;
`createTrip:723` — 90 строк, где инлайн-шаблон `buildJsonObject` является единственным
местом, где вообще описана схема payload.

**Дисциплины диспетчеров нет:** все 54 suspend-функции `TripRepository` выполняются
на контексте вызывающего, то есть на том, который взял composable.

**Сборка** (`mobile/settings.gradle.kts`, `mobile/app/build.gradle.kts`,
`mobile/gradle/libs.versions.toml`): один модуль `:app`, AGP 8.8.2, Kotlin 2.0.21,
Compose BOM 2024.12.01, Gradle 8.13, JVM 17, `minSdk 26` / `compileSdk 36`.
Version catalog используется — новые зависимости добавлять туда (сейчас мимо каталога
прописаны две: `material-icons-extended` и `lifecycle-runtime-compose:2.8.7`).
`isMinifyEnabled = false` даже в release. Lint/detekt/ktlint/spotless/`.editorconfig` — нет.

**Что уже доступно, новых зависимостей не требуется:** `navigation-compose` 2.8.5 уже
подключён и транзитивно даёт `lifecycle-viewmodel-compose`, то есть ViewModel доступен
из коробки. Также Ktor 3.0.3, kotlinx.serialization, Supabase SDK 3.0.3, Coil 3.0.4,
Mapbox 11.7.1.

**CI не защищает Android вообще.** `.github/workflows/android-release.yml` запускается
**только вручную** (`workflow_dispatch`). Ни push, ни PR не собирают приложение и не гоняют
тесты — сломанная сборка обнаружится не раньше попытки релиза. Для захода «одним куском»
это значит, что проверка целиком на нас.

**Тесты сегодня:** 10 файлов, 34 кейса, только `kotlin("test")`, никаких моков, Robolectric
и coroutine-test, каталога `androidTest` не существует. Покрыты чистые функции: разбор
диплинков, merge payload, расписание маршрута (`TripRouteScheduleTest` — самый ценный),
нормализация ссылок на фото, каталоги городов и достопримечательностей. **Не покрыто
ничего из `TripRepository` (2 031 строка), `SupabaseClient` (476) и 99.9% `OdysseyApp.kt`.**

## Целевая структура

Модуль остаётся один (`:app`) — многомодульность заказчиком не выбрана. Разделение
по пакетам внутри `com.odyssey.travelplanner`:

```
ui/
  theme/          Color.kt, Type.kt, Dimens.kt, OdysseyTheme.kt   ← 261-318 + 1336-1387
  i18n/           Localized.kt + ~45 localized* мапперов          ← 319-1085
  icons/          OdysseyIcons.kt (11 Canvas-иконок)              ← 1157-1335
  components/     OdysseyTextField, OdysseyDateField, OdysseyCalendarDialog,
                  OdysseyCatalogSheet, OdysseyMapCard, PhotoViewer,
                  StateCards (loading/empty/error)                ← дедупликация
  navigation/     OdysseyRoute (sealed), TripTab (enum), OdysseyNavHost
  screen/
    auth/         AuthScreen, RememberedAccountsPanel, ResetPasswordScreen, AuthViewModel
    trips/        MyTripsScreen, TripListCard, NewTripCard, TripsViewModel
    account/      AccountSettingsScreen, AccountSettingsSheet, AccountViewModel
    createtrip/   CreateTripScreen + шиты, CreateTripViewModel
    trip/         TripOverviewScreen (хост), TripOverviewViewModel
      overview/   OverviewContent + блоки, OverviewViewModel
      route/      TripRouteContent + шиты, RouteViewModel
      sights/     SightsContent + шиты, SightsViewModel
      restaurants/RestaurantsContent + шиты, RestaurantsViewModel
      lodging/    AccommodationContent + шиты, AccommodationViewModel
      budget/     BudgetContent + шиты, BudgetViewModel
      members/    MembersContent, MembersViewModel
      photos/     PhotosContent, PhotosViewModel
domain/
  model/          TripRole, RestaurantStatus, AccommodationStatus, BudgetCategory (enum'ы)
  RestaurantFilter.kt, BudgetMath.kt, TripDates.kt, SightRoute.kt, MapLinks.kt
data/
  di/             AppContainer
  ...             существующие репозитории
```

**Ключевые решения:**

1. **DI — ручной контейнер, без Hilt/Koin.** `AppContainer` создаётся в новом классе
   `OdysseyApplication`, держит единственный экземпляр каждого репозитория и отдаёт их
   ViewModel'ям через `ViewModelProvider.Factory`. Не требует ни ksp/kapt, ни новых
   плагинов сборки. Побочный эффект — кэши фото наконец начинают работать, а 19-мегабайтный
   TSV городов существует в одном экземпляре.

2. **ViewModel на экран и на вкладку** (~13 штук). Состояние переезжает из composable
   в `StateFlow<XxxUiState>`, composable становится функцией от состояния. Счётчик
   `refresh++` заменяется явным методом на ViewModel. Появляется `SavedStateHandle`,
   то есть переживание смерти процесса — без единого `rememberSaveable`.

3. **Навигация**: `sealed interface OdysseyRoute` вместо строк, `enum class TripTab`
   вместо магических ключей (список вкладок описывается один раз вместо трёх). Гейт
   авторизации становится свойством графа, а не императивным `LaunchedEffect`.

4. **Доменные модели**: `TripRole`, `RestaurantStatus`, `AccommodationStatus`,
   `BudgetCategory` — enum'ы. Русские строки живут **только** в их кодеке
   (`fromWire`/`toWire`), формат хранения не меняется. Проверка прав
   `currentUserRole == "Владелец"` превращается в `role == TripRole.Owner`.

5. **Ошибки**: `sealed interface TripError` + `Result`-обёртка на границе репозитория.
   Русские пользовательские сообщения уезжают из `require`/`error` в слой UI.

6. **Общий сетевой слой**: один `Json`, один хелпер вызова Edge Function (вместо шести
   копий преамбулы), константа бакета вместо 18 литералов.

### Что осталось и почему именно это

**Шаг 7 (ViewModel'и) и слияние крупных композаблов — самые дорогие и рискованные пункты
плана.** Это не перемещение кода, а переписывание управления состоянием на 20 экранах
(383 `mutableStateOf`) и слияние пар композаблов по 400–600 строк. Каждое такое изменение
может незаметно сдвинуть вёрстку, а автоматической проверки нет — только глаз.
Сделанное до сих пор либо проверяется компилятором, либо покрыто ручным прогоном;
эти два пункта требуют экранного ревью каждого затронутого экрана.

**`AppContainer` не понадобился для главного эффекта.** Он задумывался ради живых кэшей,
но кэши починены точечно (перенесены на уровень процесса), а превращение репозиториев
в синглтоны опасно: `SupabaseTripRepository` берёт клиента текущей сессии, и удержание
одного экземпляра сломало бы переключение аккаунтов. Поэтому создание репозитория на месте
вызова здесь не дефект, а корректное поведение.

**Результат шагов 0–2:** `OdysseyApp.kt` 18 135 строк → **48 файлов**, крупнейший 1 341 строка;
корневой `OdysseyApp.kt` — 283 строки. Все 272 декларации на месте (сверка множеств —
идентичны). Импорты явные, wildcard-ов нет. Сборка и 34 теста зелёные.

Шаги 0–2 **проверяемы компилятором и сохраняют поведение**: код только перемещался,
ни одна строка логики не переписана. Начиная с шага 4 изменения становятся семантическими,
и без ручного прогона по экранам их накопление — именно тот риск, который мы ограничиваем.

## Порядок работ

Заход один, но внутренний порядок важен: шаги 0–4 проверяются компилятором и почти
не несут риска, реальный риск сосредоточен в 6–7.

0. **Подготовка.** Задать `JAVA_HOME` (JDK 17) и `ANDROID_HOME`, снять базовую сборку
   и прогнать существующие тесты, **снять инвентаризацию деклараций** (см. «Проверка»).
1. **Удалить мёртвый код** — 9 композаблов, ~807 строк. Бесплатно и проверяемо.
2. **Механический распил по пакетам** без изменения логики. Здесь есть подводный камень:
   в Kotlin `private` на верхнем уровне означает «видно в пределах файла», поэтому при
   разнесении по файлам все перекрёстно используемые декларации должны стать `internal`.
   Это массово, но проверяется компилятором.
3. **Вынести чистую логику в `domain/`** — ~1 600 строк, тоже проверяется компилятором.
   Побочный эффект: логика впервые становится тестируемой, три реализации подсчёта
   длительности поездки схлопываются в одну.
4. **Тема и стили**: 282 литерала цвета → токены, `Color(0xFFE0524B)` → `errorColor()`,
   типографика в `MaterialTheme.typography`.
5. **Дедупликация компонентов**: 3 календаря → 1, 3 каталожных шита → 1, 6 текстовых
   полей → 1–2, 4 поля даты → 1, 3 хоста Mapbox → 1, add/edit шиты ресторана → 1
   с режимом. Ожидаемое сокращение — 1 500–2 000 строк.
6. **DI-контейнер и доменные enum'ы**: `OdysseyApplication` + `AppContainer`, 86 мест
   создания репозиториев заменяются инъекцией, `interface TripRepository` начинает
   использоваться как тип.
7. **ViewModel'и и навигация**: состояние переезжает из composable, sealed-маршруты,
   enum вкладок.
8. **Починка найденных багов** (следующий раздел).
9. **Гигиена сборки**: две зависимости мимо каталога — в каталог; завести `.editorconfig`;
   добавить в CI сборку и unit-тесты на PR, чтобы следующий такой инцидент ловился
   автоматически.

## Баги, которые чиним по дороге

1. **Гонка в авторизации** — вероятная причина серии правок сессии в истории
   (`efe3abc`, `ea8e9b7`, `fd595e5`, `6ebcc35`). `private var activeClient`
   (`data/SupabaseClient.kt:113`) — обычный не-`@Volatile` `var`, мутируемый из IO-корутин
   в **14 местах**, и только часть под `restoreMutex`. `ensureActiveSession:436`,
   `finalizeAuthentication:370`, `activateRememberedAccount:398`, `removeRememberedAccount:421`
   пишут его вне мьютекса, а `MainActivity.kt:58` читает с главного потока. Соседний
   `rememberedClients` при этом аккуратно закрыт `synchronized` — блокировки внутри одного
   объекта непоследовательны. Чиним: единая дисциплина доступа, `restorePersistentSession`
   с четырьмя дублирующимися хвостами сводится к одному.
2. **Выгрузка всей таблицы поездок** — 20 мест делают
   `from("trips").select().decodeList<TripRow>().firstOrNull { it.id == id }`, то есть
   тянут всю таблицу и фильтруют на клиенте, при том что рядом есть корректный
   `loadTripRow:843` с серверной фильтрацией. Заменяем на серверную фильтрацию.
3. **Мёртвые кэши фото** — чинятся сами при переходе на DI (шаг 6).
4. **Проглатывание `CancellationException`** в 98 `runCatching` в UI и 59 в data.
5. **Дисциплина диспетчеров** — сетевые вызовы репозитория уводим с контекста composable.
6. **Авторизация по строке отображения** (`currentUserRole == "Владелец"`) → enum `TripRole`.
7. **N+1 запрос ролей** в `TripRepository.kt:456` (запрос `trip_collaborators` на каждую
   поездку) и молчаливая деградация до «нет прав» при ошибке (`:427`).

## Проверка

Тестов не пишем, поэтому проверка механическая и ручная.

**1. Инвентаризация деклараций — главный предохранитель.** До распила снять список всех
top-level деклараций исходного файла, после — объединённый список по новым файлам.
Множества обязаны совпасть с точностью до осознанно удалённых (9 мёртвых композаблов)
и схлопнутых при дедупликации. Это ловит ровно ту ошибку, что случилась в `f28be2b`.

```
git show HEAD:mobile/app/src/main/java/com/odyssey/travelplanner/ui/OdysseyApp.kt \
  | grep -nE '^(@Composable)?[[:space:]]*(private |internal )?(suspend )?(fun|class|data class|enum class|object|val|const)' \
  | sed -E 's/.*(fun|class|object|val|const) +([A-Za-z0-9_]+).*/\2/' | sort -u > before.txt
```

После распила тот же сбор по `ui/` и `domain/`, затем `diff`. Расхождения объясняются
поимённо, а не «примерно сошлось».

**2. Учёт по строкам.** Суммарный объём новых файлов ≈ 18 135 минус ~807 (мёртвый код)
минус сокращение от дедупликации. Каждая тысяча строк разницы должна иметь объяснение.

**3. Сборка и существующие тесты** (только debug-варианты — release заблокирован локально):
